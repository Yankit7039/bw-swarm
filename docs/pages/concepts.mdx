# Core concepts

Use this page as a **glossary**. Short definitions work for **everyone**; expand each accordion for **technical** detail.

<Accordion title="Template">
  **Plain language:** A **recipe** for handling one kind of work — for example “unstick this order” or “route this Jira ticket.” It includes the **steps** (including AI steps) and usually ships as a **Docker image** plus YAML.

  **Technical:** A row in **`templates`** (`template_id`, `name`, `image`, `warm_pool_ref`, optional **`workflow_yaml`**). Workflows are validated by **Pydantic** (`WorkflowSchema` in `swarm_core/schema.py`).
</Accordion>

<Accordion title="Run">
  **Plain language:** A **single execution** of a template for one business incident (one order, one ticket, etc.). You can see its status and a **timeline of events**.

  **Technical:** A row in **`runs`** with UUID **`run_id`**, **`status`**, **`payload`**, optional **`result`**, **`state`** (JSON for follow-ups), **`followup_due_at`**, **`assigned_pod`**, **`sandbox_claim_name`**.
</Accordion>

<Accordion title="Stage">
  **Plain language:** A **chapter** inside a workflow — for example “enrich data” then “investigate” then “notify.”

  **Technical:** An entry in the YAML **`stages`** array. Types include **`deterministic`**, **`hybrid`**, and **`poll_loop`**. Each stage has **`steps`** (except **`poll_loop`**, which uses **`poll_steps`** and **`escalation_ladder`**).
</Accordion>

<Accordion title="Step">
  **Plain language:** One **action** inside a stage — call a tool, ask the model, or branch on a condition.

  **Technical:** Step **`type`** is **`mcp_call`**, **`llm_agent`**, or **`condition`**. See [Stages and steps](/stages-and-steps).
</Accordion>

<Accordion title="Warm pool">
  **Plain language:** **Pre-started** workers waiting so work begins quickly instead of waiting for a new machine to start.

  **Technical:** Kubernetes **SandboxWarmPool** + **SandboxClaim** (agent-sandbox). Pools are **per template image**. See [Infrastructure](/infrastructure).
</Accordion>

<Accordion title="Adapter">
  **Plain language:** The **single service** that exposes all **integrations** (Jira, email, order systems, etc.) as **tools** the workflow can call by name.

  **Technical:** FastAPI app mounting **MCP** at **`/mcp`** (default). Tool names look like **`namespace__function`** (e.g. `jira__get_ticket`). See [Adapter service](/service-adapter) and [Adapter reference](/adapters).
</Accordion>

<Accordion title="MCP">
  **Plain language:** A **standard wire protocol** so the AI runtime can **list** and **invoke** tools over HTTP without embedding vendor SDKs inside every template.

  **Technical:** **Model Context Protocol** — swarm-core uses **Streamable HTTP** to **`ADAPTER_URL/mcp`**. The adapter registers tools at startup and mirrors metadata into **`adapter_tool_registry`**.
</Accordion>

<Accordion title="SandboxClaim">
  **Plain language:** A **request** to Kubernetes to “give me a worker pod for this run.”

  **Technical:** Custom resource **`extensions.agents.x-k8s.io`** — created by the runtime; reconciled by the agent-sandbox controller to bind a pod and surface its address for **`POST /run`**.
</Accordion>

<Accordion title="Follow-up (AgentMail)">
  **Plain language:** After an email is sent, SWARM can **wait**, then **run again** to check whether the ticket is resolved or to **nudge** on a schedule — until a limit is reached.

  **Technical:** Enabled when YAML has **`follow_up.mode: agentmail`**. Runtime’s **`followup_poller`** schedules new runs; **`followup_agentmail`** in swarm-core persists **`waiting_for_followup`**, **`followup_due_at`**, and events like **`followup_scheduled`**. See [Follow-up lifecycle](/followup-lifecycle).
</Accordion>
