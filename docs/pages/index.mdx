# What is SWARM?

**SWARM** is a multi-agent orchestration platform built for **telecom enterprises**. It runs **AI-powered workflows** where each execution happens in an **isolated Kubernetes pod**, connected to your order systems, CRM, OSS, and ticketing tools through a single **adapter** layer.

You define **what** should happen in **YAML** (stages, LLM steps, and tool calls). The platform handles **where** it runs (warm pools on EKS), **how** it is observed (runs and events in Postgres), and **how** external systems trigger work (webhooks, APIs).

## The problem it solves

Telecom operations still depend on **many legacy systems** — order management, provisioning, CRM, network inventory, and escalations. Humans spend time **chasing stuck orders**, **routing tickets**, **triaging network alarms**, and **coordinating follow-ups over email**.

SWARM automates these paths with **auditable, repeatable agent workflows** that:

- Call your systems through **mockable or real** integrations (OMS, Siebel, Ericsson, NetCracker, Jira, and more).
- Use **LLM reasoning** where judgment is needed, and **deterministic steps** where rules are clear.
- Keep **one run per incident** with a full **event trail** for compliance and debugging.

## What you get

<CardGroup cols={2}>
  <Card title="Templates" icon="📦">
    Reusable workflows (YAML + container image) per use case — e.g. stuck order resolution, ticket email routing.
  </Card>
  <Card title="Isolated runs" icon="🛡️">
    Each workflow run executes in its own pod (agent-sandbox), reducing blast radius.
  </Card>
  <Card title="Warm pools" icon="⚡">
    Pre-started pods per template cut cold-start latency when events arrive.
  </Card>
  <Card title="Adapter & MCP" icon="🔌">
    Tools are exposed as **MCP** over HTTP; workflows call them by name (`jira__get_ticket`, etc.).
  </Card>
  <Card title="Observability" icon="📊">
    Postgres stores **runs**, **run_events**, and **admin API** exposes them to the **admin console**.
  </Card>
</CardGroup>
