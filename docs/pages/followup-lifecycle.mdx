# Follow-up lifecycle (AgentMail)

When **`follow_up.mode`** is **`agentmail`** in workflow YAML, **`followup_agentmail`** in swarm-core handles **email-centric** runs: initial escalation, **timed follow-ups**, and **replies** when engineers respond in thread.

## What problem it solves

Escalations often need **more than one email**: check whether a Jira ticket **resolved**, **nudge** the thread, or **reply** to an engineer — without losing **thread identity** or **auditability**.

## Three request modes

<Tabs items={["Initial", "Follow-up", "Reply"]}>
  <div>
    **Payload hints:** `order_id` present; **no** `followup_context` / `reply_context`.

    **Behavior:** First pass — route ticket, escalate, send email; schedule **`followup_due_at`**.
  </div>
  <div>
    **Payload hints:** **`followup_context`** set.

    **Behavior:** Proactive check / nudge run (runtime **follow-up poller**).
  </div>
  <div>
    **Payload hints:** **`reply_context`** set.

    **Behavior:** Engineer replied; draft response in **AgentMail** thread.
  </div>
</Tabs>

<Callout type="warning" title="Invalid combination">
  Both **`followup_context`** and **`reply_context`** in one request → run **fails** with **`workflow_error`**.
</Callout>

## Persistence

| Column / table | Role |
|----------------|------|
| **`runs.state`** | JSON blob: counts, **`message_id`**, **`thread_id`**, contact fields, etc. |
| **`runs.followup_due_at`** | When the runtime **follow-up poller** should trigger the next pod. |
| **`runs.status`** | **`waiting_for_followup`**, **`exhausted`**, **`completed`**, **`failed`**, etc. |
| **`communication_threads`** | Maps **`channel_thread_id`** (AgentMail thread) → **`run_id`** for inbound routing. |
| **`pending_inbound_interactions`** | Queues inbound if a pod is **busy**; drained when safe. |

## Event sequence (representative)

- **`workflow_started`** (each pod execution)
- **`tool_started`** / **`tool_completed`** / **`llm_message`** — same as standard runs
- **`followup_scheduled`** — next timer set (includes **`next_followup_at`** in payload)
- **`followup_sent`** — after a proactive follow-up email sends successfully
- **`ticket_resolved`** — Jira closed on a follow-up check → **`completed`**, follow-up columns cleared
- **`followup_exhausted`** — **`follow_up_count`** reached **`limit`** while ticket still open
- **`pending_inbound_drained`** — queued messages processed after engineer reply
- **`engineer_reply_after_exhausted`** — reply handled after **`exhausted`** (no timer reset)
- **`workflow_error`** — validation or persistence failure
- **`workflow_completed`** — terminal success path where applicable

## Limits and intervals

<Callout type="info" title="YAML defaults">
  **`follow_up.limit`** — max **proactive** follow-up emails (YAML default **3**).

  **`follow_up.interval_seconds`** — spacing between **`followup_due_at`** rollovers (default **120**).
</Callout>
